# URL-Based Access Control Can Be Circumvented

## Description

This website has an unauthenticated admin panel at `/admin`, but a front-end system has been configured to block external access to that path. However, the back-end application is built on a framework that supports the `X-Original-URL` header.

To solve the lab, access the admin panel and delete the user `carlos`.

## Solution

### Step 1: Confirm the admin panel is blocked

I tried to load `/admin` directly and was blocked. The response returned was very plain and minimal, suggesting it was generated by a front-end system (such as a reverse proxy or load balancer) rather than the back-end application itself, before the request ever reached the real admin logic.

### Step 2: Test the X-Original-URL header

I sent the request to Burp Repeater. I changed the URL in the request line to `/`, and added the header:

```
X-Original-URL: /invalid
```

The application returned a "not found" response, even though the request line itself pointed to `/`. This confirmed that the back-end application was processing the effective URL from the `X-Original-URL` header rather than the actual request line, and that this header was not being stripped or validated by the front-end system that was blocking direct access to `/admin`.

### Step 3: Access the admin panel via the header

I changed the value of the header to:

```
X-Original-URL: /admin
```

With the request line still pointing to `/`, this bypassed the front-end restriction entirely, since the front-end only inspected the literal request line path, not the `X-Original-URL` header. The response returned the admin panel content.

### Step 4: Delete the user carlos

To perform the delete action, I updated the `X-Original-URL` header to point to the delete endpoint with the target username, and included a matching real query string:

```http
GET /my-account/../admin/delete?username=carlos HTTP/2
Host: 0a050073041445dd80257b4c00a90062.web-security-academy.net
X-Original-Url: /admin/delete?username=carlos
```

Sending this request deleted the user `carlos` and solved the lab.

## Root Cause

Access control for the admin panel is enforced only at the front-end layer, based on the literal path in the request line. The back-end application, however, honors the `X-Original-URL` header to determine which internal route to actually process, a feature intended for use by trusted infrastructure such as reverse proxies. Since the front-end does not validate, strip, or restrict this header, an attacker can set the request line to an allowed path while using the header to redirect the back-end to a restricted endpoint, completely bypassing the front-end's access control.

## Remediation

- Enforce access control consistently at the same layer that ultimately handles the request, ideally within the back-end application itself, rather than relying solely on a front-end system inspecting the request line.
- Do not trust framework-specific headers such as `X-Original-URL` or `X-Rewrite-URL` unless they originate from a genuinely trusted, internal source, and strip them at the network edge if they are not expected from external clients.
- Apply the principle of defense in depth: sensitive functionality should independently verify authorization at the application layer, even if a separate access control mechanism is also in place elsewhere in the request pipeline.
